# Shared account and collection service

Node24+, standard-library HTTP/SQLite/crypto only. No npm dependency install is required for the service. `node --test server/tests/*.test.mjs` from the repository root runs the service suite; `node server/index.mjs` starts a loopback service. The stable frontend contract is [contract.md](contract.md). Version0.4.4 (2026-10-25) adds catalog-priced YunGouOS WeChat payments and persistent unpaid-order maintenance. Historical simulation/manual records remain separate; rollout still requires the real private merchant configuration and channel availability.

## Authority and privacy

All accounts share one namespace across Qonlang/Qonsona. Usernames normalize ASCII case; scrypt passwords have individual random salts. Opaque30-day bearer tokens are persisted only as SHA256 digests, sessions are bounded to10, logout revokes the current token. Registrations/login and authenticated API have IP/account rate limits. Product is recorded per session using `X-Qon-App` and subsequent requests must match that stored product; it does not split user balances. New-account leaderboard participation defaults on; explicit existing opt-outs are preserved. Global/friends-only visibility is configurable and uses random public IDs/nicknames, never usernames, payment amounts or private project content.

Qonsona registration/login and every authenticated online read/write require `X-Qon-Version` exactly equal to the latest formal `Kinnuch/Qonsona` GitHub Release. The unauthenticated `/v1/client-policy?app=qonsona` supplies this requirement and the public release link. The service uses a fixed HTTPS GitHub endpoint with no credentials, no redirects, a4-second deadline and512000-byte response cap. A successful lookup authorizes at most120seconds, with single-flight concurrent refresh and bounded failure retry backoff. An expired or unavailable check fails closed (`CLIENT_POLICY_UNAVAILABLE503`); missing/old/future/prerelease client versions return `CLIENT_UPDATE_REQUIRED426`. Returned `serverTime` advances even on cache hits, preventing a desktop from extending the original policy expiry. No failure erases sessions, assets or mutation receipts; logout, health/policy and separate administrator routes are exempt from the current-client requirement.

Qonlang's current account-only client remains compatible for register/login/me/profile/logout. It cannot use its session on Qonsona collection/economy/social/home routes (`CLIENT_ROUTE_UNAVAILABLE403`), and an app-header change cannot transfer a token across products (`CLIENT_APP_MISMATCH403`). The common account namespace is unchanged. Its policy response is explicitly `legacy-auth-only`, distinct from Qonsona's `exact-latest` policy. See [contract.md](contract.md) for fields and error metadata. A version header is a compatibility claim, not binary attestation.

Qonsona 0.4.1 sends the required version header; published 0.4.0 clients need an update. Finish the header-aware client release before enabling the corresponding live server policy, then verify the actual GitHub latest metadata. The required version follows later formal releases and is not permanently pinned to0.4.1. ICP filing and HTTPS were confirmed ready on2026-10-25, when the public account routes became available. Payment rollout additionally requires the new payment protocol described below; publishing code alone does not enable it.

For deterministic service tests, `Service({policyFetch})` injects a controlled fetch. Existing domain tests use `server/tests/client-fixture.mjs`, which supplies a current-version test context and synthetic formal-release metadata; policy tests exercise missing/stale headers using the actual Service. No service unit test contacts GitHub. An explicit nonproduction-only `QON_TEST_CLIENT_VERSION` override is marked `source:test-override` and ignored in production; formal desktop clients do not accept it. Actual cloud testing should continue using the real GitHub latest policy. There is no configurable third-party lookup URL or automatic fallback to the server's package version.

SQLite runs WAL+foreign keys+busy timeout. Ledger, balance, pity, grants, payment order and idempotency result changes commit together in `BEGIN IMMEDIATE` transactions. Two connections cannot double-spend a last ticket. Each state-changing operation increments `snapshot.revision`; clients discard older revisions, including late responses or old idempotent replies. Profile edits also increment revision. Unknown input fields, invalid numbers/dates/language IDs and malformed completion events reject; clients cannot submit balances. Bounded legacy memorials use the separate explicit import described below.

Time is based on claimed active seconds intersected with recent server wall clock (max60s per event, first event initializes clock, overlapping devices cannot add overlapping time). It accepts at most7200s/day and awards2points/minute only for the first3600s (120points); any completion and two designated boards award20each (60points), default reading/review. Only completion marks a day as learning check-in. Weekly reward80requires5different days in the Monday–Sunday Asia/Shanghai week, each >=600accepted seconds and >=1task. Makeup never fabricates time/tasks or weekly qualification. Server caps restrict abuse; an untrusted desktop completion claim is not proof that a human actually learned. The client must submit only completed tasks/active intervals and must not upload project text.

Draws use cryptographic randomness. Free/support ticket balances stay separate, but both share the same SR/SSR pity pair. Source cannot be mixed inside one10draw request. Base probabilities A70/R24.4/SR5/SSR0.6%, high guarantee20, SSR soft guarantee from draw76with+5percentage points per draw, hard90; SSR wins when guarantees coincide. Non-SSR weights are normalized to70:24.4:5. Duplicate echoes1/3/8/20remain nontransferable; 1000echoes now exchange for one learning ticket. Furniture sales are reserved for a later update. Catalog includes20regular authorized test sprite cells plus month-specific exclusive companions; local legacy memorials never become economic assets or ranking value. The shop sells A240/R720points, ticket240points, makeup80points and the1000echo ticket. The old glow decoration is no longer sold; already owned decorations are retained. Makeup targets yesterday through7days ago, at most2uses/current calendar month; actual stats are untouched.

## YunGouOS WeChat payments

**0.4.4 — 2026-10-25.** Ordinary authenticated, current-version Qonsona users can create live orders when the payment switch and merchant configuration are valid. There is no administrator-only allowance or manual eligibility list. Payment is not recorded as age verification; `adult_verified` remains0 for provider orders.

The authoritative [support catalog](support-catalog.mjs) defines these immutable invoice entitlements. The old CNY60/month application cap is removed; the single-order maximum is CNY600. Independent channel limits still apply: the merchant dashboard currently shows CNY10/day, so catalog availability does not guarantee a higher-value channel payment will be accepted.

| Plan ID         |                          CNY | Base + bonus support tickets |
| --------------- | ---------------------------: | ---------------------------: |
| `first-support` |                         0.01 |                  10 + 0 = 10 |
| `support-6`     |                            6 |                  10 + 0 = 10 |
| `support-60`    |                           60 |               100 + 10 = 110 |
| `support-600`   |                          600 |            1000 + 100 = 1100 |
| `custom`        | 0.60–600 in exact 0.60 steps |       One per 0.60, no bonus |

First-payment eligibility is reserved inside the order transaction, one active promotional invoice per account. An unknown result retains it; a channel-confirmed unpaid closure releases it. A separate unique paid-winner claim never resets after refund. Any previous payment receipt, including a refunded historical one-fen/one-ticket record, excludes new promotional orders. Previously issued invoices keep their original amount/tickets; upgrading does not turn a historical one-fen/one-ticket payment into ten tickets. A promotional invoice validly reserved before a different normal order settles retains its original offer.

If an old closed promotional invoice and its replacement both become genuinely paid, the first transactional winner gets10 tickets. The other payment retains its unique receipt, becomes `approved/refund_review` with `credited_tickets=0`, and waits for operator reconciliation rather than receiving a second discount or pretending money was refunded. A later verified full refund reverses only tickets actually credited.

Keep payment configuration only in a protected server env file:

| Variable                  | Meaning                                                                                                           |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `QON_PAYMENTS_ENABLED`    | Default0; live requires1 plus valid provider configuration.                                                       |
| `QON_SUPPORT_TICKET_FEN`  | Legacy nonproduction simulated `{tickets}` pricing only; never changes the real catalog or its bonuses. Optional. |
| `QON_YUNGOUOS_MCH_ID`     | The approved WeChat merchant identifier.                                                                          |
| `QON_YUNGOUOS_PAY_KEY`    | Private YunGouOS signing key; never ship or print it.                                                             |
| `QON_YUNGOUOS_NOTIFY_URL` | HTTPS domain callback, e.g. `https://kinnuch.cn/qon-api/v1/payments/yungouos/notify`; no port, query or fragment. |
| `QON_TEST_GRANTS`         | Set0 for production. Production always rejects the grant route even if misconfigured as1.                         |

Also use `NODE_ENV=production`, a fresh protected `QON_DB`, loopback binding and the trusted HTTPS proxy configuration in [deploy/env.example](deploy/env.example). A requested live mode with missing/invalid merchant configuration fails closed; it does not silently become simulation. Nonproduction with payments disabled can create explicitly `testing:true` simulation orders, but must not show a real payment QR. Test grants cannot be combined with live mode. Merchant keys, bearer tokens and admin secrets stay out of client bundles, repository files, screenshots and logs.

The main process sends `X-Qon-Payment-Protocol: yungouos-wechat-v2` for live `POST /v1/support/orders {requestId,planId,amountFen?}`. Only custom plans accept an integer-fen `amountFen`; fixed plans reject client amounts, ticket counts and bonuses. Old `{tickets}` bodies are retained only for nonproduction simulation. Missing/wrong payment protocol returns `PAYMENT_CLIENT_UPDATE_REQUIRED409` before reservation or provider I/O. This is compatibility metadata, not a credential or binary attestation. Normal auth/current-version/owner checks remain required; auth, reads and callbacks do not require this payment header.

Creation persists the original amount, base/bonus tickets, request receipt and stable merchant order number before network I/O. Native `type=1` returns only a validated `weixin://wxpay/bizpayurl?pr=...` payload, encoded locally using [qrcode-generator](../resources/licenses/qrcode-generator-MIT.txt). The channel request explicitly sets `auto=0` (no profit sharing), outside its required four-field signature, and omits sharing configuration and unsupported forced-expiry parameters. No merchant key or remote QR-image service is used by the desktop.

An uncertain create returns HTTP200 with the same zero-credit `creating` reservation, without invented QR or success. Replay never resends Native with another number. Owners can recover the order and explicitly check or close it. Closing queries first: paid settles, unknown stays unresolved, and only confirmed unpaid channel closure becomes `rejected/closed`. Even a closed invoice can be explicitly checked for late payment when its callback was lost. Hiding the dialog never closes or replaces an invoice.

Each account may have only one pending real order; another create returns `SUPPORT_ORDER_PENDING409`, while same-request replay remains valid. After ten minutes, an exact channel-query “支付订单不存在” response can cancel a never-issued-QR `creating` reservation only if it has no receipt, payment reference or persisted verified paid claim; audit status is `absent`, not a fabricated channel-close success. QR-issued invoices, signed paid evidence and ordinary timeout/unknown responses stay unresolved; late genuine payment still follows normal verified settlement.

`expiresAt=createdAt+600000` is the authoritative ten-minute checkout deadline. The server starts a persistent maintenance worker at startup and checks due invoices every30seconds, one per worker window. It actively queries before closing an unpaid invoice; a paid result settles its original entitlement. Cross-process leases, a merchant-wide12-second query cooldown and persistent exponential retry/backoff prevent duplicate work and survive restart. Valid callbacks needing a query take priority; already-settled notification replays do not extend that priority. Channel failures/unknown states remain unresolved, not falsely closed. The channel does not enforce this deadline itself; outages or a queue can delay confirmation after ten minutes, and genuine late payments still reconcile.

The public form-urlencoded callback is `POST /v1/payments/yungouos/notify`; duplicate fields are rejected. The official keyed-MD5 signature covers exactly `code,orderNo,outTradeNo,payNo,money,mchId`; unsigned metadata is never payment authority. Verify it, then query the fixed HTTPS channel endpoint and match merchant, original order, integer amount and unique transaction before atomic receipt/approval/credit. No network I/O holds a SQLite transaction. A transaction funds only one order; repeats and separate database connections cannot double credit. Authenticated repeats matching already-recorded paid/refunded receipts return exact text `SUCCESS` without recredit or fresh priority; unconfirmed events return `FAIL`. Callbacks are exempt from sessions/version gating so releases and logout cannot strand valid payments. QR display, screenshots and client claims do not establish payment.

There is no outgoing automated refund or automatic discovery of every dashboard refund. The protected operator endpoint `POST /v1/admin/support/orders/:id/check-refund {requestId,refundNo}` only reads and verifies channel refund evidence against the original merchant/order/amount/transaction. Full unused refunds reverse actual credited tickets; partial or consumed refunds enter `refund_review`, retain the collection and freeze support spending in the same transaction as deduction. Refund evidence arriving before the original paid callback still records the unique receipt and permanently consumes first-payment eligibility, without issuing tickets. Legacy `/approve`, `/reject` and `/refund` all reject provider-backed orders; production additionally rejects any legacy manual approval. These routes cannot initiate money transfers and are blocked publicly.

Schema additions preserve existing amounts, entitlements and assets: plan/base/bonus fields, `credited_tickets`, provider status, close retry metadata, active `first_support_reservations` and permanent `first_support_claims`. Only the initial missing-column migration backfills old approved credits from their original ticket count (other statuses0); reopening never rewrites a new review row's explicit zero credit. Back up the entire database consistently before deploying a schema change.

Public transport requires TLS with valid certificates; nginx overwrites trusted proxy headers and forwards only to loopback. The sandboxed/context-isolated renderer uses restricted IPC; tokens are main-owned and OS-encrypted for persistence, never stored as plaintext fallback. Signing secrets remain only in permission-protected server configuration (directory0700/file0600); this is access control, not encryption at rest. The channel's legacy signature, private host/OS and TLS trust remain dependencies; no absolute security guarantee is made.

### Production identity cutover

The test-to-production identity cutover retains account identity/password hashes, public IDs and profile/privacy fields in a fresh database, keeping test assets in a private backup. Sessions are not copied, so sign in again. Do not copy test wallets/rewards/collection/pity or balance-bearing responses. This cutover rule is not a repeated upgrade reset: subsequent production upgrades retain actual production receipts, orders, wallets and account assets, including the original one-fen/one-ticket payment history. Local learning files are not deleted.

Old `(user_id,request_id)` pairs are imported only into `retired_test_requests`. `Store.mutate` checks these tombstones inside its write transaction before replay/mutation and returns `RETIRED_TEST_REQUEST409` without executing stale test operations. No old tokens or success responses are copied. Verify migration and financial reconciliation independently of local test results.

## Generic deployment example

For a fresh production deployment, inspect the host/site before applying these generic examples. The actual mycloud isolated testing deployment is recorded below. Copy this `server` directory to `/opt/qonaccounts`; use a dedicated unprivileged `qonaccounts` service user and `/var/lib/qonaccounts` with0700permissions. Place [deploy/env.example](deploy/env.example) as `/etc/qonaccounts.env`, owned by root and readable by service only. Generate the admin secret on the server and keep it outside repository/client packages. Do not paste secrets into logs, issue reports, URL query strings or command history.

Use the [systemd example](deploy/qonaccounts.service) after confirming the actual Node24executable location. Add only the scoped [nginx locations](deploy/nginx.conf.example) to the existing HTTPS site; validate nginx configuration before reload. Public base `https://kinnuch.cn/qon-api` forwards to loopback `/v1`. The backend in production accepts requests only from a trusted loopback TLS proxy; do not expose its port to WAN. Clients must restrict the production HTTPS origin, validate certificates and deny token-bearing redirects. There is no browser CORS allowance.

`NODE_ENV=production` always makes `/v1/test/grant`404 and health.testing.grantsEnabledfalse, even when `QON_TEST_GRANTS=1`. Health also returns payments.enabled/simulation. An isolated test service with its own DB, `NODE_ENV=test`, `QON_TEST_GRANTS=1` grants100learning tickets per new requestId without a lifetime limit; replaying a request returns its original result. Do not point a test service at the production DB, promote test economy data into real balances, or use a frontend keyword as server authorization.

Back up the SQLite database using SQLite online backup or stop the service before a consistent copy; copying only the live `.sqlite` without WAL is unsafe. Keep token/password tables and admin credentials protected, retain financial audit records, monitor DB size/rate-limit failures and review retention policy. Automatic backups and email password recovery are not implemented. Account recovery therefore needs a separately authorized operator process; do not expose an unauthenticated reset route. A single Node process is sufficient initially; the current leaderboard scans opt-in accounts and should be indexed/materialized before high-volume rollout.

### Daily plans and legacy memorial migration

Daily completion rewards require any activity plus two designated boards, default reading/review,20 points each (max60). POST `/v1/tasks/configure` changes the two distinct boards once before learning begins; request IDs are idempotent. Historical points remain intact. Weekly reward requires five real days with >=600 seconds and at least one completion each.

Authenticated POST `/v1/collection/legacy` explicitly synchronizes at most12 whitelisted old companion memorials, merging earliest records into snapshot.legacy. They grant no currency, tickets, pity progress or leaderboard value. No private projects/languages are uploaded. See contract.md for payloads/errors. Old persisted states migrate lazily without schema changes.

## Weekly pools and home update (2026-10-13)

Each seven-day pool contains every regular A/R/SR and one featured SSR. Period zero starts2026-10-12 at00:00 Asia/Shanghai; snapshot.drawPool has id/startAt/endAt/ssrIds/characterIds, with endAt exclusive. The database persists a private random schedule seed, a shuffled SSR order for each complete cycle and the issued pool snapshots. Each SSR appears once per cycle; the next cycle cannot start with the previous cycle's final SSR when at least two SSRs exist. A started cycle is fixed even when a new SSR is added to catalog; the next cycle admits the new catalog entries. Account/device/restart cannot reroll the schedule. Do not remove characters already referenced by current pool/cycle records; retire a character only through a future explicit migration. Back up the schedule tables together with the account database.

Draw expectedPoolId rejects a stale uncommitted confirmation before spending tickets; committed same-request replay returns its original result and poolId after refresh. The poolId is retained in private draw history. The probability and pity rules are unchanged, and monthly-exclusive companions remain outside ordinary pools. The client renders the pool as a horizontal gallery with the actual SSR under the center spotlight.

Home is separate from the upbringing companion. Its account-wide layout stores a skinId and normalized0–1 placements of at most30 distinct owned companion types, including owned monthly companions. POST /home/update requires the prior home revision to prevent overwriting another device's changes. Duplicate/unowned companions, nonfinite/out-of-room positions and forged furniture fields reject without writes. Retried committed layouts return their original receipt without restoring an old room over a newer layout. Old accounts lazily receive the empty room-placeholder skin, retaining every prior decoration. Author-editable home-skins.json defines the current placeholder and the future skin catalog; there is no skin/furniture price or purchase route yet. The default placeholder is owned by every account. Furniture remains an empty array for future implementation.
