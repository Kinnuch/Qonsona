# Shared account and collection service

Node24+, standard-library HTTP/SQLite/crypto only. No npm dependency install required. `node --test server/tests/*.test.mjs` from repository root runs the service suite; `node server/index.mjs` starts a loopback service. The stable frontend contract is [contract.md](contract.md). This is a manual payment verification ledger, not an automatic WeChat payment integration.

## Authority and privacy

All accounts share one namespace across Qonlang/Qonsona. Usernames normalize ASCII case; scrypt passwords have individual random salts. Opaque30-day bearer tokens are persisted only as SHA256 digests, sessions are bounded to10, logout revokes the current token. Registrations/login and authenticated API have IP/account rate limits. Product is recorded per session using `X-Qon-App` and subsequent requests must match that stored product; it does not split user balances. New-account leaderboard participation defaults on; explicit existing opt-outs are preserved. Global/friends-only visibility is configurable and uses random public IDs/nicknames, never usernames, payment amounts or private project content.

Qonsona registration/login and every authenticated online read/write require `X-Qon-Version` exactly equal to the latest formal `Kinnuch/Qonsona` GitHub Release. The unauthenticated `/v1/client-policy?app=qonsona` supplies this requirement and the public release link. The service uses a fixed HTTPS GitHub endpoint with no credentials, no redirects, a4-second deadline and512000-byte response cap. A successful lookup authorizes at most120seconds, with single-flight concurrent refresh and bounded failure retry backoff. An expired or unavailable check fails closed (`CLIENT_POLICY_UNAVAILABLE503`); missing/old/future/prerelease client versions return `CLIENT_UPDATE_REQUIRED426`. Returned `serverTime` advances even on cache hits, preventing a desktop from extending the original policy expiry. No failure erases sessions, assets or mutation receipts; logout, health/policy and separate administrator routes are exempt from the current-client requirement.

Qonlang's current account-only client remains compatible for register/login/me/profile/logout. It cannot use its session on Qonsona collection/economy/social/home routes (`CLIENT_ROUTE_UNAVAILABLE403`), and an app-header change cannot transfer a token across products (`CLIENT_APP_MISMATCH403`). The common account namespace is unchanged. Its policy response is explicitly `legacy-auth-only`, distinct from Qonsona's `exact-latest` policy. See [contract.md](contract.md) for fields and error metadata. A version header is a compatibility claim, not binary attestation.

For deterministic service tests, `Service({policyFetch})` injects a controlled fetch. Existing domain tests use `server/tests/client-fixture.mjs`, which supplies a current-version test context and synthetic formal-release metadata; policy tests exercise missing/stale headers using the actual Service. No service unit test contacts GitHub. An explicit nonproduction-only `QON_TEST_CLIENT_VERSION` override is marked `source:test-override` and ignored in production; formal desktop clients do not accept it. Actual cloud testing should continue using the real GitHub latest policy. There is no configurable third-party lookup URL or automatic fallback to the server's package version.

SQLite runs WAL+foreign keys+busy timeout. Ledger, balance, pity, grants, payment order and idempotency result changes commit together in `BEGIN IMMEDIATE` transactions. Two connections cannot double-spend a last ticket. Each state-changing operation increments `snapshot.revision`; clients discard older revisions, including late responses or old idempotent replies. Profile edits also increment revision. Unknown input fields, invalid numbers/dates/language IDs and malformed completion events reject; clients cannot submit balances. Bounded legacy memorials use the separate explicit import described below.

Time is based on claimed active seconds intersected with recent server wall clock (max60s per event, first event initializes clock, overlapping devices cannot add overlapping time). It accepts at most7200s/day and awards2points/minute only for the first3600s (120points); any completion and two designated boards award20each (60points), default reading/review. Only completion marks a day as learning check-in. Weekly reward80requires5different days in the Monday–Sunday Asia/Shanghai week, each >=600accepted seconds and >=1task. Makeup never fabricates time/tasks or weekly qualification. Server caps restrict abuse; an untrusted desktop completion claim is not proof that a human actually learned. The client must submit only completed tasks/active intervals and must not upload project text.

Draws use cryptographic randomness. Free/support ticket balances stay separate, but both share the same SR/SSR pity pair. Source cannot be mixed inside one10draw request. Base probabilities A70/R24.4/SR5/SSR0.6%, high guarantee20, SSR soft guarantee from draw76with+5percentage points per draw, hard90; SSR wins when guarantees coincide. Non-SSR weights are normalized to70:24.4:5. Duplicate echoes1/3/8/20remain nontransferable; 1000echoes now exchange for one learning ticket. Furniture sales are reserved for a later update. Catalog includes20regular authorized test sprite cells plus month-specific exclusive companions; local legacy memorials never become economic assets or ranking value. The shop sells A240/R720points, ticket240points, makeup80points and the1000echo ticket. The old glow decoration is no longer sold; already owned decorations are retained. Makeup targets yesterday through7days ago, at most2uses/current calendar month; actual stats are untouched.

Support orders are pending until a separate authorized operator verifies actual receipt, adulthood, amount and unique payment transaction reference. Default price600fen/ticket, maximum6000fen of pending/approved orders per account/month. Production order creation/approval is disabled unless `QON_PAYMENTS_ENABLED=1` after the operator establishes a real age-verification/consumer process. The default nonproduction mode creates explicitly `testing:true` simulation orders only, requires synthetic `QA-` references for approval, and must not display a real QR or request actual payment. Admin approval requires `adultVerified:true`, recording an independent verification, not treating a checkbox as proof. Switching to real payment cannot credit old simulated orders. No screenshot, static QR scan, client checkbox or frontend payment-success response credits a ticket. Admin key is a separate deployment secret, never a client credential. The admin HTTP namespace should stay blocked at public nginx; trusted operations run through an SSH tunnel/loopback. Approval/refund ledger mutations are idempotent; one payment reference cannot credit two orders. Refund endpoint records an already verified refund and reverses unused credit conservatively; after any support spend since approval it requires manual review and does not silently remove a won character. It does not initiate a money transfer. Age verification, the precise sales/consumer policy and handling disputes remain operator responsibilities; do not claim a self-declared age checkbox independently proves adulthood.

## Generic deployment example

For a fresh production deployment, inspect the host/site before applying these generic examples. The actual mycloud isolated testing deployment is recorded below. Copy this `server` directory to `/opt/qonaccounts`; use a dedicated unprivileged `qonaccounts` service user and `/var/lib/qonaccounts` with0700permissions. Place [deploy/env.example](deploy/env.example) as `/etc/qonaccounts.env`, owned by root and readable by service only. Generate the admin secret on the server and keep it outside repository/client packages. Do not paste secrets into logs, issue reports, URL query strings or command history.

Use the [systemd example](deploy/qonaccounts.service) after confirming the actual Node24executable location. Add only the scoped [nginx locations](deploy/nginx.conf.example) to the existing HTTPS site; validate nginx configuration before reload. Public base `https://kinnuch.cn/qon-api` forwards to loopback `/v1`. The backend in production accepts requests only from a trusted loopback TLS proxy; do not expose its port to WAN. Clients must restrict the production HTTPS origin, validate certificates and deny token-bearing redirects. There is no browser CORS allowance.

`NODE_ENV=production` always makes `/v1/test/grant`404 and health.testing.grantsEnabledfalse, even when `QON_TEST_GRANTS=1`. Health also returns payments.enabled/simulation. An isolated test service with its own DB, `NODE_ENV=test`, `QON_TEST_GRANTS=1` grants100learning tickets per new requestId without a lifetime limit; replaying a request returns its original result. Do not point a test service at the production DB, promote test economy data into real balances, or use a frontend keyword as server authorization.

Back up the SQLite database using SQLite online backup or stop the service before a consistent copy; copying only the live `.sqlite` without WAL is unsafe. Keep token/password tables and admin credentials protected, retain financial audit records, monitor DB size/rate-limit failures and review retention policy. Automatic backups, email password recovery and official merchant callbacks are not implemented. Account recovery therefore needs a separately authorized operator process; do not expose an unauthenticated reset route. A single Node process is sufficient initially; the current leaderboard scans opt-in accounts and should be indexed/materialized before high-volume rollout.

### Daily plans and legacy memorial migration

Daily completion rewards require any activity plus two designated boards, default reading/review,20 points each (max60). POST `/v1/tasks/configure` changes the two distinct boards once before learning begins; request IDs are idempotent. Historical points remain intact. Weekly reward requires five real days with >=600 seconds and at least one completion each.

Authenticated POST `/v1/collection/legacy` explicitly synchronizes at most12 whitelisted old companion memorials, merging earliest records into snapshot.legacy. They grant no currency, tickets, pity progress or leaderboard value. No private projects/languages are uploaded. See contract.md for payloads/errors. Old persisted states migrate lazily without schema changes.

## Weekly pools and home update (2026-10-13)

Each seven-day pool contains every regular A/R/SR and one featured SSR. Period zero starts2026-10-12 at00:00 Asia/Shanghai; snapshot.drawPool has id/startAt/endAt/ssrIds/characterIds, with endAt exclusive. The database persists a private random schedule seed, a shuffled SSR order for each complete cycle and the issued pool snapshots. Each SSR appears once per cycle; the next cycle cannot start with the previous cycle's final SSR when at least two SSRs exist. A started cycle is fixed even when a new SSR is added to catalog; the next cycle admits the new catalog entries. Account/device/restart cannot reroll the schedule. Do not remove characters already referenced by current pool/cycle records; retire a character only through a future explicit migration. Back up the schedule tables together with the account database.

Draw expectedPoolId rejects a stale uncommitted confirmation before spending tickets; committed same-request replay returns its original result and poolId after refresh. The poolId is retained in private draw history. The probability and pity rules are unchanged, and monthly-exclusive companions remain outside ordinary pools. The client renders the pool as a horizontal gallery with the actual SSR under the center spotlight.

Home is separate from the upbringing companion. Its account-wide layout stores a skinId and normalized0–1 placements of at most30 distinct owned companion types, including owned monthly companions. POST /home/update requires the prior home revision to prevent overwriting another device's changes. Duplicate/unowned companions, nonfinite/out-of-room positions and forged furniture fields reject without writes. Retried committed layouts return their original receipt without restoring an old room over a newer layout. Old accounts lazily receive the empty room-placeholder skin, retaining every prior decoration. Author-editable home-skins.json defines the current placeholder and the future skin catalog; there is no skin/furniture price or purchase route yet. The default placeholder is owned by every account. Furniture remains an empty array for future implementation.
