# Shared accounts and collection API v1

All routes use `/v1`. JSON UTF-8, body <=32KiB, errors `{error:{code,message}}` with stable English `code`; successful data are returned directly (no `data` wrapper). The provider notification below is the form/text exception. Authentication uses `Authorization: Bearer <opaque token>` held by the desktop main process. Production uses the fixed HTTPS origin with valid certificates, no credential-bearing redirects, and a loopback service behind TLS nginx. No browser CORS/API credentials are shipped. This is the0.4.4 contract (2026-10-25); actual payment availability also depends on private configuration and channel limits.

## Current Qonsona client requirement

`GET /client-policy?app=qonsona` requires no login or version header and returns:

```json
{
  "app": "qonsona",
  "mode": "exact-latest",
  "currentVersion": "0.4.1",
  "source": "github-latest",
  "checkedAt": 1791936000000,
  "serverTime": 1791936010000,
  "validUntil": 1791936120000,
  "releaseUrl": "https://github.com/Kinnuch/Qonsona/releases/tag/v0.4.1"
}
```

The version above illustrates the format; the server fetches the actual latest formal GitHub Release at the fixed `https://api.github.com/repos/Kinnuch/Qonsona/releases/latest`. It does not use the server package version or a client-submitted target version. Drafts, prereleases, noncanonical semantic versions, missing publication dates and release URLs outside this exact repository/tag are rejected. Lookup uses no credentials, rejects redirects, limits response size to512000bytes and times out after4seconds. Concurrent requests share one lookup. Successful metadata remains valid for120seconds; `checkedAt` and `validUntil` are fixed for that lookup, while each returned `serverTime` is the current server time. Clients calculate the remaining lifetime from `validUntil-serverTime`, using elapsed time rather than their local wall clock. Once expired, any lookup failure returns `CLIENT_POLICY_UNAVAILABLE503`; an old success is never used indefinitely. Failure retries back off from10seconds to at most120seconds.

Version0.4.1 clients send the required header. Published0.4.0 clients do not and must update before using the gated service. Complete the header-aware client release before enabling the corresponding live policy, then validate the deployed endpoint. The policy tracks the latest formal release rather than a fixed0.4.1 value. Public account routes became available with ICP/HTTPS on2026-10-25; this does not by itself enable payments or establish payment acceptance.

Send `X-Qon-App:qonsona` and `X-Qon-Version:<actual app version>` on registration, login and every authenticated online route, including snapshot/profile reads, rankings, friends, learning, shop, draws, upbringing and home. The version must equal `currentVersion` exactly; a missing header, old version, future version, prerelease version or version prefixed with `v` returns HTTP426:

```json
{
  "error": {
    "code": "CLIENT_UPDATE_REQUIRED",
    "message": "CLIENT_UPDATE_REQUIRED",
    "currentVersion": "0.4.1",
    "releaseUrl": "https://github.com/Kinnuch/Qonsona/releases/tag/v0.4.1"
  }
}
```

These failures do not remove sessions, collections, wallet balances, XP, home layouts or prior mutation receipts. Clients must keep unresolved journals and refrain from sending/replaying online mutations until a fresh policy authorizes the actual client version. `/health`, `/client-policy`, the separate administrator namespace and authenticated `POST /auth/logout` remain available without a current-version match. Logout still revokes only its own valid token. Session product must match `X-Qon-App`; changing the header on an existing token returns `CLIENT_APP_MISMATCH403`.

Qonlang is a separate product and currently retains its existing five basic account operations: registration, login, `GET /auth/me`, `PATCH /auth/me`, and logout. These legacy routes do not require a version header. `GET /client-policy?app=qonlang` describes `mode:'legacy-auth-only'`, `currentVersion:null`, `source:'legacy-account-compatibility'` and the Qonlang release URL; it must not be treated as authorization for Qonsona. A Qonlang session cannot call collection, economy, rankings, friends, upbringing or home routes (`CLIENT_ROUTE_UNAVAILABLE403`), and cannot become a Qonsona session by changing its app header. Shared usernames/accounts and existing assets are retained. This is a compatibility boundary for the current Qonlang account client, not an assertion that its release number equals Qonsona's.

An explicit `QON_TEST_CLIENT_VERSION` override exists only when `NODE_ENV !== production`, uses `source:'test-override'` and never pretends to be GitHub verification. Production ignores it. Formal desktop clients accept only the actual `github-latest` source. Unit tests inject their own fetch and current-version contexts; they never call GitHub. Versions are protocol compatibility claims, not signed attestation of a client binary.

## Identity and snapshot

`POST /auth/register {username,password,nickname?}` and `/auth/login {username,password}` return `{token,expiresAt,user,snapshot}`. User: `{id,username,nickname,publicId,publicCollection,publicTime,rankVisibility,createdAt}`. Username is case-insensitive ASCII `[a-z0-9_]{3,32}`, password 10–128 chars. Username is private; rankings and friend profiles show nickname and random publicId. `POST /auth/logout {}` revokes this session. `GET /auth/me` returns `{user,snapshot}`. `PATCH /auth/me {nickname?,publicCollection?,publicTime?,rankVisibility?}` changes only supplied fields. New accounts default both participation flags true and visibility `global`. Visibility `friends` restricts participation to the accepted-friends board. Either board can be disabled with its participation flag. Migration preserves every existing false participation flag, because old false values may be explicit opt-outs.

## Guest starter and account synchronization

The desktop collection remains browsable without signing in. A guest may choose one regular A (初识) companion for free, stored in the local application profile. This local trial does not authorize online purchases, draws or support orders. Attempts to acquire another companion, draw or create a support order require login. Guest progress is not an economic balance and must never be submitted as server-owned points, tickets, echoes, pity, XP or keepsakes.

`POST /collection/starter {requestId,characterId}` requires an authenticated Qonsona session and the exact current client version, just like all other collection mutations. `characterId` must identify a regular A companion in the server catalog; R/SR/SSR, monthly-exclusive and unknown IDs return `INVALID_STARTER_CHARACTER400`. All extra fields are rejected. The result is `{characterId,snapshot}`; `snapshot.starter` contains the account's permanent `{characterId,claimedAt,source:'guest-starter'}` marker, with Unix-millisecond claimedAt. Older accounts without this marker remain unchanged when read; the optional field is omitted until the first claim. No SQL schema replacement or asset import is needed.

Each account can claim exactly one starter. The first valid claim adds one owned companion and records its source as `guest-starter`. If the same companion was already owned, its original count, timestamp and source stay unchanged; the marker is recorded without granting duplicates or echoes. No points, tickets, XP, pity, learning time or task completion is granted. An empty current-companion slot is set to this starter with zero initial XP; an existing selected companion and any prior progress are preserved. Once a marker exists, any fresh valid A claim returns the existing starter ID and a current snapshot, even when the requested ID differs; it never grants a second companion. The client must accept this existing ID rather than overwrite it with the guest's choice. Normal same-requestId idempotency returns the original receipt, while reusing that ID with another payload returns `IDEMPOTENCY_CONFLICT409`. Ownership, marker, selection, ledger and receipt transact atomically, including requests from different devices.

The desktop main process keeps the claim in its existing durable mutation journal before sending it. Unknown results, revoked sessions, rate limits, malformed replies, version changes or service failures retain the same request ID and payload for recovery. Definitive business rejections clear the journal. Successful replies must match the authenticated account; the returned characterId must match snapshot.starter and a positively owned regular A entry. Login success itself is retained when starter synchronization cannot complete. The main process reports local `AccountSession.starterSync:'pending'` separately, and only binds the local starter to the real account after a confirmed result; this status is not a server health flag or asset grant.

For production rollout, deploy and verify the starter-aware server route before publishing the corresponding client. Keep the server's exact-latest policy tied to the actual formal release, and do not use a test version override in production. A client talking to an older server may sign in successfully but receive `NOT_FOUND404` for starter sync; it must keep the local companion pending and retry after a server update, without silently discarding the guest choice or treating login as failed. Desktop UI verification uses an isolated local service; this contract alone does not imply payment availability.

## Learning, shop, draw

`POST /reward/activity {requestId,language,seconds,completion?:{kind,id}}`: seconds integer 0–60; language one of ja/en/fr/ko/es/ar/ru/gd/qya/sjn or `qonlang:<stable-pack-id>`. Kinds reading/practice/courses/review. `requestId` globally unique per account and mutation family; replays return the original response, mismatched payload returns IDEMPOTENCY_CONFLICT. Heartbeat is bounded by server elapsed time since previous activity across all devices (first heartbeat initializes clock and earns no time). Daily accepted time <=7200s, time reward 2 points/min <=120; Three daily goals earn20 each, max60: any genuine completion plus the two designated kinds (default reading and review). One reading completion satisfies any+reading for40; further readings cannot substitute for review. today.tasks remains the numeric distinct-event count. First true completion checks in. At least five different actual days in a Monday–Sunday week, each with >=600 seconds and >=1 completion, earn80 once; makeup does not count toward weekly bonus. Client event claims cannot be cryptographically proven; this is bounded accounting, not a claim of cheat-proof learning verification.

`POST /shop/purchase {requestId,itemId,quantity?,expectedPrice?}`: `ticket` (240 points → one learning ticket), `echo-ticket` (1000 echoes → one learning ticket), `makeup` (80 points), `character:<A-id>` (240), `character:<R-id>` (720). Each Shanghai day one regular A/R has a stable, server-selected 50% offer shared across users and devices. Snapshot supplies final price, originalPrice and discount0.5. Optional expectedPrice is the confirmed unit price; mismatch (for example after midnight) returns SHOP_PRICE_CHANGED409 before deduction, requiring a refreshed confirmation. Unknown client price fields are rejected. Max quantity10; character quantity1 and already owned characters cannot be repurchased; makeup stock<=3. No furniture/decoration is sold yet; old owned decoration:glow remains in inventory.

`POST /draw {requestId,source:'learning'|'support',count:1|10,expectedPoolId?}` returns `{results:[{id,tier,duplicate,echoes}],poolId,snapshot}`. Only the selected source is spent, and both sources share the same pair of pity counters. Base A70/R24.4/SR5/SSR0.6%; high-tier (SR/SSR) guaranteed at20; SSR draw76 is5.6%, rises5 percentage points per draw until draw89=70.6%, draw90=100%. SSR check precedes high pity; non-SSR weights use70:24.4:5 normalized, or SR-only on high guarantee. SSR resets both counters, SR resets high counter. Duplicate echoes A1/R3/SR8/SSR20; not cash or transferable credit, exchangeable at the fixed1000echo ticket rate.

The draw pool refreshes every seven days starting2026-10-12T00:00:00+08:00. startAt/endAt are Unix milliseconds; endAt is exclusive. Each pool includes all regular A/R/SR and exactly one featured SSR. SSRs are shuffled without replacement for one complete cycle before another shuffle; consecutive periods do not repeat the SSR, including the boundary between cycles when the catalog has at least two SSRs. Persistent private seed, cycle order and pool receipts are global for every account/device and survive service restart. A started cycle is retained if a new SSR is added; the following cycle uses the updated catalog. Monthly-exclusive companions never enter the pool. Current clients submit the snapshot drawPool.id as expectedPoolId; a different active ID returns DRAW_POOL_CHANGED409 before deduction and requires refreshed user confirmation. An already committed request is replayed before the pool guard, retaining its original poolId and old snapshot; new requests after rollover use the new pool. Draw ledger.detail.poolId records which pool produced each draw. Old historical draws may lack poolId.

`POST /inventory/use {requestId,itemId:'makeup',day}` consumes one item, only yesterday through7days ago, <=2 uses per calendar month, only unchecked day. Creates makeup checkin only; never changes actual seconds/task totals, weekly bonus or monthly task eligibility. `GET /leaderboards?kind=collection|time&language=<id>&limit=20&scope=global|friends`: collection ignores optional language; time without language shows all-language total; supplied language is exact-matched. Friends scope includes self and mutually accepted friends, never strangers or pending invitations. Global scope excludes friends-only visibility. Both scopes honor the relevant participation flag. Returns `{kind,language,scope,rows:[{rank,publicId,nickname,value,currentCompanion:character|null}]}`. No username, account ID, credentials or payment data are disclosed. Seconds are server-capped lifetime accepted per-language totals.

## Support payments, administration and isolated tests

Snapshot optionally includes `payments:{enabled,provider:'yungouos'|null,mode:'live'|'simulation'|'disabled',currency:'CNY',unitAmountFen:60,orderMaxFen:60000,monthLimitFen:null,eligible,plans,firstPurchase,custom}`. Each plan is `{id,name:{zh,en},amountFen,baseTickets,bonusTickets,tickets,firstPurchaseOnly}`. `firstPurchase` is `{eligible:boolean,claimed:boolean,pendingOrderId?:uuid}`; claimed means a historical payment receipt exists, including refunded receipts. `custom` is `{minAmountFen:60,maxAmountFen:60000,stepAmountFen:60,ticketAmountFen:60}`. General `eligible` means an ordinary authenticated account, without an administrator whitelist or age-verification claim. Missing capability must not be treated as permission to pay. Live mode requires the explicit switch and complete private merchant configuration; production disables test grants and simulation. See [deployment](README.md#yungouos-wechat-payments).

Live creation is `POST /support/orders {requestId,planId,amountFen?}` and requires `X-Qon-Payment-Protocol: yungouos-wechat-v2`, ordinary session auth and the exact latest client version. Missing/wrong protocol returns `PAYMENT_CLIENT_UPDATE_REQUIRED409` before reservation/provider I/O. It is compatibility metadata, not a credential or authentic-binary proof. Only `custom` accepts `amountFen`; fixed plans reject any client-supplied amount/tickets/bonus/merchant/currency. Old `{tickets}` input and `QON_SUPPORT_TICKET_FEN` pricing remain only in nonproduction legacy simulation and never override the real catalog.

| planId          |                       amountFen |  baseTickets | bonusTickets |      tickets |
| --------------- | ------------------------------: | -----------: | -----------: | -----------: |
| `first-support` |                               1 |           10 |            0 |           10 |
| `support-6`     |                             600 |           10 |            0 |           10 |
| `support-60`    |                            6000 |          100 |           10 |          110 |
| `support-600`   |                           60000 |         1000 |          100 |         1100 |
| `custom`        | Integer60–60000, divisible by60 | amountFen/60 |            0 | amountFen/60 |

The old6000fen/month application cap is removed; each order is at most60000fen. Channel limits remain independent (the merchant dashboard shows CNY10/day as of2026-10-25), so a valid catalog amount does not promise channel acceptance. Invalid plan/step/number/fields use `INVALID_SUPPORT_PLAN`, `INVALID_SUPPORT_AMOUNT`, `INVALID_NUMBER` or `INVALID_FIELDS`.

Creation transactionally permits only one pending real order per account (`SUPPORT_ORDER_PENDING409`); same-request replay is checked first. Exact fixed-endpoint query JSON `code:1,msg:'支付订单不存在'` may cancel an expired (at least ten minutes) `creating` reservation only if no QR was ever stored and no receipt/reference/persisted verified paid claim exists: record local `rejected/closed` with `provider_status:'absent'`, release any active promotion, and preserve an audit ledger entry without credit or a channel-close call. HTTP404, other messages/errors, QR-issued orders or signed paid evidence do not authorize absence cancellation. Late real payment remains reconcilable under the existing unique-receipt/promotion-winner rules.

First-payment creation atomically locks one active reservation per user; unknown results retain it, confirmed unpaid closure releases it. Existing payment receipts, even refunded historical one-fen/one-ticket transactions, exclude new offers. A valid reserved invoice keeps its agreed entitlement if a normal package happens to settle first. Successful promotional settlement claims a separate unique permanent user winner; refund never restores the allowance. If two valid promotional invoices become paid after closure/replacement, only the first winner credits10; the other retains its receipt and becomes `approved/refund_review` with zero credited tickets, requiring real channel refund reconciliation. No payment fact is discarded or fake refund asserted. `FIRST_SUPPORT_UNAVAILABLE409` rejects another ineligible promotional create. Old invoices are not repriced or topped up.

Returns `{order,snapshot}`. Order remains `{id,tickets,amountFen,currency:'CNY',status:'pending'|'approved'|'rejected'|'refunded',testing,createdAt,approvedAt,payment?}`, with optional `planId,baseTickets,bonusTickets` for new invoices; historical fields remain unchanged. Provider `payment` is `{provider:'yungouos',method:'wechat',state:'creating'|'pending'|'paid'|'closed'|'refund_review'|'refunded',qrCodeUrl?,expiresAt?}`. QR payloads are bounded native WeChat links rendered locally. The client displays them only for payable pending invoices within their deadline. `refund_review` is not a claim that tickets arrived. Native uses `auto=0`, no sharing configuration and no unsupported forced-expiry parameter. `adult_verified` remains0. `GET /support/orders` lists only the authenticated owner's orders.

Creation commits its reservation, original amount/entitlement and stable merchant number before network I/O. Unknown creation returns HTTP200 with the same uncredited `creating` order and no invented QR; same-ID replay never resends Native or changes package. This confirms local reservation only and clears the desktop create journal. `POST /support/orders/:id/check {}` is an owner/current-version read, returning `{order,snapshot}`; closed invoices can still discover genuine late payment. Queries use a persistent merchant12-second cooldown; cached state can be returned during cooldown, or `PAYMENT_CHECK_BUSY503` while pending authenticated callbacks have priority. `POST /support/orders/:id/close {requestId}` queries first, settles paid invoices and closes only channel-confirmed unpaid ones. Unknown results retain the reservation. Dismissing a screen is not closure or consent to another order.

`expiresAt=createdAt+600000` is a ten-minute server deadline. Startup and a30-second maintenance worker process due invoices without a client window, using persistent cross-process leases, retry counts and exponential backoff (up to15minutes). The worker queries before channel close; paid invoices settle and unknown/failed checks stay pending. One query slot per worker window leaves room for genuine callbacks; authenticated unsettled callbacks take priority, while recorded paid/refunded notification repeats do not renew it. Deadlines/retries survive restart and old longer pending deadlines shorten without changing price/tickets. This is active maintenance rather than channel-enforced expiry; failures or queueing can delay confirmed closure, and local expiry never proves money was unpaid.

`POST /payments/yungouos/notify` accepts form-urlencoded, <=32KiB, with duplicate fields rejected. It needs no bearer, app/version or payment-protocol header. Verify the channel's keyed-MD5 signature over exactly `code,orderNo,outTradeNo,payNo,money,mchId`, then independently query the fixed HTTPS endpoint and match the original merchant/order/integer amount/transaction. Unsigned metadata, screenshots, QR display and client success are not evidence. Approval, unique receipt, ledger, promotion winner and actual credit share one SQLite transaction without network I/O. Duplicate callbacks, polling and separate connections cannot double credit or reuse one transaction for another order. Exact text `SUCCESS` acknowledges verified settlement or a matching recorded paid/refunded duplicate without recredit; other events return `FAIL` and an error status. Simulated orders never become real credit.

Admin routes require a separate server-only bearer and stay blocked publicly. Legacy `GET /admin/support/orders` lists pending records. All provider-backed legacy `/approve`, `/reject` and `/refund` actions return `PAYMENT_PROVIDER_VERIFICATION_REQUIRED409`; production also prohibits provider-less legacy manual approval. Nonproduction simulation retains its synthetic `QA-` reference/audit rules. No management route initiates a money transfer.

There is no outgoing automated refund or blanket discovery of dashboard refunds. `POST /admin/support/orders/:id/check-refund {requestId,refundNo}` reads channel refund evidence matching merchant/original order/amount/transaction. Full unused refunds reverse actual `credited_tickets`, never advertised but unissued tickets. Partial/consumed refunds enter `refund_review`, retain the collection and freeze support spending inside its deduction transaction. Verified refunds arriving before the original paid callback still record the unique receipt/reference and consume first-payment eligibility with zero credit; a later matching paid callback is acknowledged without recredit. Ordinary payment queries cannot replace refund verification.

Schema additions are order plan/base/bonus/`credited_tickets`, provider query status and auto-close retry fields, plus active `first_support_reservations` and permanent `first_support_claims`. Only the initial missing-column migration backfills approved historical credits from their original tickets (other statuses0); later reopenings preserve explicit zero-credit review records. Original amounts/tickets/assets do not change. Test-to-production cutover may retain identity/password/profile data but excludes test assets/sessions/responses, importing only old request tombstones. `RETIRED_TEST_REQUEST409` rejects those IDs before replay/mutation. Subsequent production upgrades retain actual receipts, orders and assets; local learning files remain unaffected.

`POST /test/grant {requestId}`: adds100 learning tickets on every distinct request ID; same-ID retry returns the original response and never credits twice. Allowed only `NODE_ENV !== production && QON_TEST_GRANTS=1`, with normal account auth and rate limits. Always404 in production. The client generates a fresh ID for each explicit keyword Enter action. This is not an admin credential or a frontend permission shortcut.

All economic mutations transact SQLite ledger+balances+idempotency response atomically. Unknown properties rejected. No client balance, probability, pity or paid history upload endpoint. Legacy memorial migration below accepts only bounded personal decorations.

`GET /health` (no authentication): `{status:'ok',testing:{grantsEnabled:boolean},payments:{enabled:boolean,simulation:boolean}}`. GrantsEnabled is alwaysfalse in production. The current catalog has a60000fen single-order maximum and no application monthly cap. Snapshot.history is the latest50 server ledger records, private to owner. `revision:number` strictly increases on each committed mutation/profile edit, even in the same millisecond; clients reject lower revisions. Idempotent replay returns the original response/revision after the version requirement is satisfied. Completion-only seconds0does not advance the heartbeat clock, except first initialization. All timestamp fields are Unix milliseconds, not seconds or ISO strings. `today.tasks` is a number of unique completed events. Shop types are ticket/makeup/character/decoration. `drawRules` exact fields are exported in server/domain.mjs RULES. Nickname1–40trim; usernames ASCII case-insensitive; session expiry30days. `X-Qon-App:qonlang|qonsona` selects and binds the session product (defaults toqonsona if omitted); Qonsona additionally requires `X-Qon-Version`. Mutations return `{snapshot,...route-specific-result}`.

## Friends and upbringing

`GET /friends` returns `{friends:[profile],incoming:[{id,profile,createdAt}],outgoing:[{id,profile,createdAt}],ownPublicId}`. Profile contains `{publicId,nickname,currentCompanion:character|null}` only. POST `/friends/request {requestId,publicId}` creates an invitation using a random public ID; cannot invite self, existing friends, or duplicate/reverse pending invitations. Each user can have at most50 pending invitations and200 accepted friends. POST `/friends/respond {requestId,invitationId,accept:boolean}` is authorized only for the recipient; acceptance atomically creates both friendship edges. Rejection creates neither edge. POST `/friends/remove {requestId,publicId}` removes both edges. Mutations return `{friends,snapshot}` and normal idempotency replay. Counterpart snapshot revisions also advance, so another device can refresh social state without replacing economic balances.

POST `/companion/select {requestId,characterId,expectedCurrentId?}` requires the companion to be owned; it selects the account-wide current companion and initializes its progress. Optional expectedCurrentId may be null for the initial empty selection; if supplied it must match the current selection inside the transaction, otherwise COMPANION_CHANGED409 rejects without changing selection. Selection persists across devices and appears on leaderboard/friend profiles. POST `/companion/answer {requestId,language,answerId,correct:true,characterId?}` reports a correctly answered question instance. Optional characterId binds the answer to the companion selected when it was answered; when supplied it must match the current owned selection inside the transaction, otherwise COMPANION_CHANGED409 rejects without XP, gifts or an answer receipt. New clients supply both guards and keep them unchanged for retry. An already committed same-requestId response is returned before guard revalidation, so recovering its original outcome cannot undo a later selection or duplicate XP. The stable instance answerId must survive retry and undo/re-answer; receipt uniqueness is `(user,language,answerId)` and persists across devices, days and service restarts. Distinct request IDs cannot multiply XP for that same answer instance. Accepted answers grant5XP only to the selected companion, max200 answers/day shared across all companions. Duplicate answers return `accepted:false,xp:0`. Results contain `{accepted,xp,gifts:string[],characterId,snapshot}`. Five milestones at100/300/700/1500/3000XP grant nontransferable, noneconomic keepsakes once per companion; they mint no points, tickets, echoes or draw progress. A companion never has more than five keepsakes. Server validates ownership, accepted language, claimed correctness shape, duplicate receipts and cap; without a server question bank these bounded client completion claims are not proof against forged study events.

Monthly exclusive reward requires every natural calendar day of that month to have all three task-plan entries complete with a real-learning checkin. Any one completion or a makeup stamp alone cannot qualify. Server awards the monthly companion automatically and once when the final qualifying day completes. Leap years and month lengths are derived from the calendar. Snapshot.monthly provides the qualifying days, required count, reward ID and whether it was awarded. Past makeup or client imports cannot fill missing monthly tasks. This is a separate special reward, excluded from normal draws/shop and pity counters.

Gallery supplies three server-backed slides: the daily selection from the newest released regular batch, the current discounted A/R, and the most-owned regular SSR (distinct owning users, duplicates do not add popularity). Aggregate counts contain no owner identity. Visual carousel timing, manual dots, frame style and nearest-neighbor pixel rendering belong to the client.

## Home

POST `/home/update {requestId,expectedRevision,skinId,placements:[{characterId,x,y}]}` stores the account's independent home layout and returns `{homeRevision,snapshot}`. expectedRevision is required, a nonnegative safe integer matching snapshot.home.revision; mismatch returns HOME_CHANGED409. Each x/y is a finite number in0–1 representing a normalized in-room position. At most30 distinct owned companion types can be placed, including owned monthly companions. Unknown/unowned companions return CHARACTER_NOT_OWNED403; duplicates return DUPLICATE_HOME_CHARACTER; malformed/oversized placements return INVALID_HOME_PLACEMENTS; invalid coordinates return INVALID_HOME_POSITION. skinId must exist in the server home-skins.json catalog and be owned in inventory.homeSkins, otherwise INVALID_HOME_SKIN403. The placeholder room-placeholder is owned by every account. No skin/furniture sales or client-submitted furniture fields exist yet; furniture remains an empty array. Failed writes do not change room, revision, ledger or any economic balance. Same-request replay returns its original outcome before guard validation and cannot overwrite a newer saved room. Old accounts lazily receive an empty placeholder layout without discarding prior inventory or draw history. Home fields never appear on public profiles or rankings.
