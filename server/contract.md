# Shared accounts and collection API v1

All routes use `/v1`. JSON UTF-8, body <=32KiB, errors `{error:{code,message}}` with stable English `code`; successful data are returned directly (no `data` wrapper). Authentication uses `Authorization: Bearer <opaque token>` held by the desktop main process. Production clients must use the configured HTTPS origin; never forward a bearer to another origin or allow invalid certificates. Server listens on loopback behind TLS nginx in production. No browser CORS/API credentials are shipped.

## Current Qonsona client requirement

`GET /client-policy?app=qonsona` requires no login or version header and returns:

```json
{
  "app": "qonsona",
  "mode": "exact-latest",
  "currentVersion": "0.4.1",
  "source": "github-latest",
  "checkedAt": 1791936000000,
  "serverTime": 1791936010000,
  "validUntil": 1791936120000,
  "releaseUrl": "https://github.com/Kinnuch/Qonsona/releases/tag/v0.4.1"
}
```

The version above illustrates the format; the server fetches the actual latest formal GitHub Release at the fixed `https://api.github.com/repos/Kinnuch/Qonsona/releases/latest`. It does not use the server package version or a client-submitted target version. Drafts, prereleases, noncanonical semantic versions, missing publication dates and release URLs outside this exact repository/tag are rejected. Lookup uses no credentials, rejects redirects, limits response size to512000bytes and times out after4seconds. Concurrent requests share one lookup. Successful metadata remains valid for120seconds; `checkedAt` and `validUntil` are fixed for that lookup, while each returned `serverTime` is the current server time. Clients calculate the remaining lifetime from `validUntil-serverTime`, using elapsed time rather than their local wall clock. Once expired, any lookup failure returns `CLIENT_POLICY_UNAVAILABLE503`; an old success is never used indefinitely. Failure retries back off from10seconds to at most120seconds.

Version0.4.1 clients send the required header. Published0.4.0 clients do not and must update before using the gated service. Complete the header-aware client release before enabling the corresponding live policy, then validate the deployed endpoint; this contract does not claim that rollout is complete. The policy tracks the latest formal release rather than a fixed0.4.1 value. Public registration remains unavailable while kinnuch.cn ICP filing and HTTPS are pending.

Send `X-Qon-App:qonsona` and `X-Qon-Version:<actual app version>` on registration, login and every authenticated online route, including snapshot/profile reads, rankings, friends, learning, shop, draws, upbringing and home. The version must equal `currentVersion` exactly; a missing header, old version, future version, prerelease version or version prefixed with `v` returns HTTP426:

```json
{
  "error": {
    "code": "CLIENT_UPDATE_REQUIRED",
    "message": "CLIENT_UPDATE_REQUIRED",
    "currentVersion": "0.4.1",
    "releaseUrl": "https://github.com/Kinnuch/Qonsona/releases/tag/v0.4.1"
  }
}
```

These failures do not remove sessions, collections, wallet balances, XP, home layouts or prior mutation receipts. Clients must keep unresolved journals and refrain from sending/replaying online mutations until a fresh policy authorizes the actual client version. `/health`, `/client-policy`, the separate administrator namespace and authenticated `POST /auth/logout` remain available without a current-version match. Logout still revokes only its own valid token. Session product must match `X-Qon-App`; changing the header on an existing token returns `CLIENT_APP_MISMATCH403`.

Qonlang is a separate product and currently retains its existing five basic account operations: registration, login, `GET /auth/me`, `PATCH /auth/me`, and logout. These legacy routes do not require a version header. `GET /client-policy?app=qonlang` describes `mode:'legacy-auth-only'`, `currentVersion:null`, `source:'legacy-account-compatibility'` and the Qonlang release URL; it must not be treated as authorization for Qonsona. A Qonlang session cannot call collection, economy, rankings, friends, upbringing or home routes (`CLIENT_ROUTE_UNAVAILABLE403`), and cannot become a Qonsona session by changing its app header. Shared usernames/accounts and existing assets are retained. This is a compatibility boundary for the current Qonlang account client, not an assertion that its release number equals Qonsona's.

An explicit `QON_TEST_CLIENT_VERSION` override exists only when `NODE_ENV !== production`, uses `source:'test-override'` and never pretends to be GitHub verification. Production ignores it. Formal desktop clients accept only the actual `github-latest` source. Unit tests inject their own fetch and current-version contexts; they never call GitHub. Versions are protocol compatibility claims, not signed attestation of a client binary.

## Identity and snapshot

`POST /auth/register {username,password,nickname?}` and `/auth/login {username,password}` return `{token,expiresAt,user,snapshot}`. User: `{id,username,nickname,publicId,publicCollection,publicTime,rankVisibility,createdAt}`. Username is case-insensitive ASCII `[a-z0-9_]{3,32}`, password 10–128 chars. Username is private; rankings and friend profiles show nickname and random publicId. `POST /auth/logout {}` revokes this session. `GET /auth/me` returns `{user,snapshot}`. `PATCH /auth/me {nickname?,publicCollection?,publicTime?,rankVisibility?}` changes only supplied fields. New accounts default both participation flags true and visibility `global`. Visibility `friends` restricts participation to the accepted-friends board. Either board can be disabled with its participation flag. Migration preserves every existing false participation flag, because old false values may be explicit opt-outs.

`GET /collection` returns snapshot:

```
{version:1,revision,serverTime,day,user,balances:{points,tickets:{learning,support},echoes},
 pity:{sinceSSR,sinceHigh},
 characters:[{id,count,firstAt,source}],legacy:[{id,day,at,minutes}],inventory:{makeup,decorations:string[],homeSkins:string[]},
 checkins:[{day,kind:'learning'|'makeup'}],
 today:{seconds,timePoints,taskPoints,tasks,taskPlan:[{id,kind,done,reward:20}],planChanges,weeklyBonus},
 totals:{seconds,collectionCount},catalog:[{id,tier,sheet,cell,name:{zh,en},speciesId,biography,sprite?,special?,month?}],
 species:[{id,name:{zh,en},characterIds}],
 shop:[{id,price,currency:'points'|'echoes',type,characterId?,tier?,originalPrice?,discount?}],drawRules:{...},
 gallery:[{type:'new'|'discount'|'popular',characterId,date,price?,originalPrice?,ownerCount?}],
 companion:{currentId,progress:[{characterId,xp,gifts:string[]}],todayAnswers,maxDailyAnswers:200,xpPerAnswer:5,milestones:[{xp,id,name:{zh,en}}]},
 monthly:{month,completedDays:string[],requiredDays,rewardId,claimed},
 drawPool:{id,startAt,endAt,ssrIds:string[],characterIds:string[]},
 home:{revision,skinId,placements:[{characterId,x,y}],furniture:[]},
 homeSkins:[{id,name:{zh,en},owned:boolean}],
 history:[{id,kind,at,detail}]}
```

Regular Language Companions use `companion-1`…`companion-20`; each tier A/R/SR/SSR has five. All existing IDs, sheets and sprite dimensions are preserved. Eight figures use explicit rectangles in sprite sheet 2. Author-confirmed `speciesId` groups are `cat` (1,2,3,7,8,9), `dog` (4,5,10,11), `frog` (6,12), `dragon` (13,14,15,17,18,19,20), and `bird` (16 plus monthly). Chinese display names are 灵动猫、逐风狗、鸣诗鸟、听雨蛙、星辉龙, with series names editable in `server/species.json`. Individual names/speciesId and empty introduction/traits/story biography fields are author-editable in `server/catalog.json`; no biography prose is generated. Current-month `monthly-YYYY-MM` plus owned previous-month companions are added to snapshot catalog, with `special:'monthly'` and month. The monthly Clear-Sky Bird uses separate blue art and is excluded from ordinary draws and shop; subsequent months use a different ID and month frame until the author supplies distinct art. Stable IDs retain existing ownership, XP, home placements and draw receipts despite renamed companions or changed series. `sprite` rectangles have `{x,y,width,height,sheetWidth,sheetHeight}`. All dates, offers and weekly boundaries use Asia/Shanghai (UTC+08); week starts Monday. Online economy state is never restored by client JSON import.

## Learning, shop, draw

`POST /reward/activity {requestId,language,seconds,completion?:{kind,id}}`: seconds integer 0–60; language one of ja/en/fr/ko/es/ar/ru/gd/qya/sjn or `qonlang:<stable-pack-id>`. Kinds reading/practice/courses/review. `requestId` globally unique per account and mutation family; replays return the original response, mismatched payload returns IDEMPOTENCY_CONFLICT. Heartbeat is bounded by server elapsed time since previous activity across all devices (first heartbeat initializes clock and earns no time). Daily accepted time <=7200s, time reward 2 points/min <=120; Three daily goals earn20 each, max60: any genuine completion plus the two designated kinds (default reading and review). One reading completion satisfies any+reading for40; further readings cannot substitute for review. today.tasks remains the numeric distinct-event count. First true completion checks in. At least five different actual days in a Monday–Sunday week, each with >=600 seconds and >=1 completion, earn80 once; makeup does not count toward weekly bonus. Client event claims cannot be cryptographically proven; this is bounded accounting, not a claim of cheat-proof learning verification.

`POST /shop/purchase {requestId,itemId,quantity?,expectedPrice?}`: `ticket` (240 points → one learning ticket), `echo-ticket` (1000 echoes → one learning ticket), `makeup` (80 points), `character:<A-id>` (240), `character:<R-id>` (720). Each Shanghai day one regular A/R has a stable, server-selected 50% offer shared across users and devices. Snapshot supplies final price, originalPrice and discount0.5. Optional expectedPrice is the confirmed unit price; mismatch (for example after midnight) returns SHOP_PRICE_CHANGED409 before deduction, requiring a refreshed confirmation. Unknown client price fields are rejected. Max quantity10; character quantity1 and already owned characters cannot be repurchased; makeup stock<=3. No furniture/decoration is sold yet; old owned decoration:glow remains in inventory.

`POST /draw {requestId,source:'learning'|'support',count:1|10,expectedPoolId?}` returns `{results:[{id,tier,duplicate,echoes}],poolId,snapshot}`. Only the selected source is spent, and both sources share the same pair of pity counters. Base A70/R24.4/SR5/SSR0.6%; high-tier (SR/SSR) guaranteed at20; SSR draw76 is5.6%, rises5 percentage points per draw until draw89=70.6%, draw90=100%. SSR check precedes high pity; non-SSR weights use70:24.4:5 normalized, or SR-only on high guarantee. SSR resets both counters, SR resets high counter. Duplicate echoes A1/R3/SR8/SSR20; not cash or transferable credit, exchangeable at the fixed1000echo ticket rate.

The draw pool refreshes every seven days starting2026-10-12T00:00:00+08:00. startAt/endAt are Unix milliseconds; endAt is exclusive. Each pool includes all regular A/R/SR and exactly one featured SSR. SSRs are shuffled without replacement for one complete cycle before another shuffle; consecutive periods do not repeat the SSR, including the boundary between cycles when the catalog has at least two SSRs. Persistent private seed, cycle order and pool receipts are global for every account/device and survive service restart. A started cycle is retained if a new SSR is added; the following cycle uses the updated catalog. Monthly-exclusive companions never enter the pool. Current clients submit the snapshot drawPool.id as expectedPoolId; a different active ID returns DRAW_POOL_CHANGED409 before deduction and requires refreshed user confirmation. An already committed request is replayed before the pool guard, retaining its original poolId and old snapshot; new requests after rollover use the new pool. Draw ledger.detail.poolId records which pool produced each draw. Old historical draws may lack poolId.

`POST /inventory/use {requestId,itemId:'makeup',day}` consumes one item, only yesterday through7days ago, <=2 uses per calendar month, only unchecked day. Creates makeup checkin only; never changes actual seconds/task totals, weekly bonus or monthly task eligibility. `GET /leaderboards?kind=collection|time&language=<id>&limit=20&scope=global|friends`: collection ignores optional language; time without language shows all-language total; supplied language is exact-matched. Friends scope includes self and mutually accepted friends, never strangers or pending invitations. Global scope excludes friends-only visibility. Both scopes honor the relevant participation flag. Returns `{kind,language,scope,rows:[{rank,publicId,nickname,value,currentCompanion:character|null}]}`. No username, account ID, credentials or payment data are disclosed. Seconds are server-capped lifetime accepted per-language totals.

## Manual support, administration, isolated tests

`POST /support/orders {requestId,tickets}` creates a pending manual-verification order (1–100 tickets, server price `QON_SUPPORT_TICKET_FEN`, default600fen), returns `{order:{id,tickets,amountFen,currency:'CNY',status,testing,createdAt,approvedAt},snapshot}`. The6000fen monthly cap limits the actual quantity. `GET /support/orders` returns `{orders}` for this account. Production rejects order creation/approval unless `QON_PAYMENTS_ENABLED=1` (default0). Nonproduction with payments disabled creates simulation-only orders with `testing:true`; UI must not ask for real payment or show a real payment QR. A QR/screenshot/client payment button never grants credit. Authorized operator must independently verify receipt and adulthood.

Admin routes use a separate `Authorization: Bearer <QON_ADMIN_KEY>`, never shipped to clients. `GET /admin/support/orders?status=pending`; `POST /admin/support/orders/:id/approve {requestId,paymentReference,amountFen,adultVerified:true}` must match expected amount; actual transaction reference unique across orders. The administrator's flag records independent verification, not a claim that a checkbox proves age. Simulation reference must start `QA-`; switching modes cannot approve an old testing order as real. Credits support tickets exactly once. `POST .../reject {requestId}`; `POST .../refund {requestId}` only succeeds before any support draw or spend on that order's credited balance (conservative account-level consumed check); payment refund must be performed separately by operator, this endpoint records confirmed refund and reverses credit. Disputed/already-consumed refunds require documented manual handling; do not silently erase collections.

`POST /test/grant {requestId}`: adds100 learning tickets on every distinct request ID; same-ID retry returns the original response and never credits twice. Allowed only `NODE_ENV !== production && QON_TEST_GRANTS=1`, with normal account auth and rate limits. Always404 in production. The client generates a fresh ID for each explicit keyword Enter action. This is not an admin credential or a frontend permission shortcut.

All economic mutations transact SQLite ledger+balances+idempotency response atomically. Unknown properties rejected. No client balance, probability, pity or paid history upload endpoint. Legacy memorial migration below accepts only bounded personal decorations.

`GET /health` (no authentication): `{status:'ok',testing:{grantsEnabled:boolean},payments:{enabled:boolean,simulation:boolean}}`. GrantsEnabled is alwaysfalse in production. Support orders have a6000fen/month cap (pending plus approved count, rejected/refunded do not). Snapshot.history is the latest50 server ledger records, private to owner. `revision:number` strictly increases on each committed mutation/profile edit, even in the same millisecond; clients reject lower revisions. Idempotent replay returns the original response/revision after the version requirement is satisfied. Completion-only seconds0does not advance the heartbeat clock, except first initialization. All timestamp fields are Unix milliseconds, not seconds or ISO strings. `today.tasks` is a number of unique completed events. Shop types are ticket/makeup/character/decoration. `drawRules` exact fields are exported in server/domain.mjs RULES. Nickname1–40trim; usernames ASCII case-insensitive; session expiry30days. `X-Qon-App:qonlang|qonsona` selects and binds the session product (defaults toqonsona if omitted); Qonsona additionally requires `X-Qon-Version`. Mutations return `{snapshot,...route-specific-result}`.

## Daily designated plan and old memorials

`POST /tasks/configure {requestId,kinds:[kind,kind]}`: exactly two distinct reading/practice/courses/review kinds. Once per Asia/Shanghai day, before accepted learning seconds or any completion/reward. Returns `{kinds,snapshot}`. Same request replay is idempotent; another change returns TASK_PLAN_CHANGE_LIMIT, learning begun returns TASK_PLAN_LOCKED, invalid kinds return INVALID_TASK_PLAN. today.planChanges is0 or1. today.taskPlan uses stable IDs any/board-1/board-2 and kind/done/reward20. Done derives from stored completion keys. Historical task points are preserved without awards exceeding60. Weekly qualification remains five days with at least600 accepted seconds and any genuine completion, independent of designated boards.

`POST /collection/legacy {requestId,unlocks:[{id,day,at,minutes}]}` requires login. Only companion-1 through companion-12, at most12 distinct IDs per batch. minutes is numeric5/15/30; day is valid nonfuture YYYY-MM-DD and at is nonnegative nonfuture integer Unix milliseconds. Original local timezone may differ; day and at need not map to the same Shanghai day. Unknown fields rejected. Returns `{imported,snapshot}`; imported counts submitted records, not economic grants. Merge by ID preserves earliest timestamp across sessions/devices. snapshot.legacy defaults to[] for old accounts. Errors INVALID_LEGACY/INVALID_LEGACY_ENTRY/INVALID_LEGACY_DATE or generic INVALID_FIELDS/INVALID_BODY.

Clients require explicit sync of old memorials, never automatic private project uploads. Free personal memorials have no trading or ranking value; client claims cannot prove authenticity. They never enter the new draw pool, characters/collectionCount, balances, tickets, echoes, either pity counter, checkins or leaderboards. Different accounts may keep the same memorial. The endpoint is not arbitrary asset import.

## Friends and upbringing

`GET /friends` returns `{friends:[profile],incoming:[{id,profile,createdAt}],outgoing:[{id,profile,createdAt}],ownPublicId}`. Profile contains `{publicId,nickname,currentCompanion:character|null}` only. POST `/friends/request {requestId,publicId}` creates an invitation using a random public ID; cannot invite self, existing friends, or duplicate/reverse pending invitations. Each user can have at most50 pending invitations and200 accepted friends. POST `/friends/respond {requestId,invitationId,accept:boolean}` is authorized only for the recipient; acceptance atomically creates both friendship edges. Rejection creates neither edge. POST `/friends/remove {requestId,publicId}` removes both edges. Mutations return `{friends,snapshot}` and normal idempotency replay. Counterpart snapshot revisions also advance, so another device can refresh social state without replacing economic balances.

POST `/companion/select {requestId,characterId,expectedCurrentId?}` requires the companion to be owned; it selects the account-wide current companion and initializes its progress. Optional expectedCurrentId may be null for the initial empty selection; if supplied it must match the current selection inside the transaction, otherwise COMPANION_CHANGED409 rejects without changing selection. Selection persists across devices and appears on leaderboard/friend profiles. POST `/companion/answer {requestId,language,answerId,correct:true,characterId?}` reports a correctly answered question instance. Optional characterId binds the answer to the companion selected when it was answered; when supplied it must match the current owned selection inside the transaction, otherwise COMPANION_CHANGED409 rejects without XP, gifts or an answer receipt. New clients supply both guards and keep them unchanged for retry. An already committed same-requestId response is returned before guard revalidation, so recovering its original outcome cannot undo a later selection or duplicate XP. The stable instance answerId must survive retry and undo/re-answer; receipt uniqueness is `(user,language,answerId)` and persists across devices, days and service restarts. Distinct request IDs cannot multiply XP for that same answer instance. Accepted answers grant5XP only to the selected companion, max200 answers/day shared across all companions. Duplicate answers return `accepted:false,xp:0`. Results contain `{accepted,xp,gifts:string[],characterId,snapshot}`. Five milestones at100/300/700/1500/3000XP grant nontransferable, noneconomic keepsakes once per companion; they mint no points, tickets, echoes or draw progress. A companion never has more than five keepsakes. Server validates ownership, accepted language, claimed correctness shape, duplicate receipts and cap; without a server question bank these bounded client completion claims are not proof against forged study events.

Monthly exclusive reward requires every natural calendar day of that month to have all three task-plan entries complete with a real-learning checkin. Any one completion or a makeup stamp alone cannot qualify. Server awards the monthly companion automatically and once when the final qualifying day completes. Leap years and month lengths are derived from the calendar. Snapshot.monthly provides the qualifying days, required count, reward ID and whether it was awarded. Past makeup or client imports cannot fill missing monthly tasks. This is a separate special reward, excluded from normal draws/shop and pity counters.

Gallery supplies three server-backed slides: the daily selection from the newest released regular batch, the current discounted A/R, and the most-owned regular SSR (distinct owning users, duplicates do not add popularity). Aggregate counts contain no owner identity. Visual carousel timing, manual dots, frame style and nearest-neighbor pixel rendering belong to the client.

## Home

POST `/home/update {requestId,expectedRevision,skinId,placements:[{characterId,x,y}]}` stores the account's independent home layout and returns `{homeRevision,snapshot}`. expectedRevision is required, a nonnegative safe integer matching snapshot.home.revision; mismatch returns HOME_CHANGED409. Each x/y is a finite number in0–1 representing a normalized in-room position. At most30 distinct owned companion types can be placed, including owned monthly companions. Unknown/unowned companions return CHARACTER_NOT_OWNED403; duplicates return DUPLICATE_HOME_CHARACTER; malformed/oversized placements return INVALID_HOME_PLACEMENTS; invalid coordinates return INVALID_HOME_POSITION. skinId must exist in the server home-skins.json catalog and be owned in inventory.homeSkins, otherwise INVALID_HOME_SKIN403. The placeholder room-placeholder is owned by every account. No skin/furniture sales or client-submitted furniture fields exist yet; furniture remains an empty array. Failed writes do not change room, revision, ledger or any economic balance. Same-request replay returns its original outcome before guard validation and cannot overwrite a newer saved room. Old accounts lazily receive an empty placeholder layout without discarding prior inventory or draw history. Home fields never appear on public profiles or rankings.
